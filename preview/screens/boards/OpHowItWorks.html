How it works

One token set, two adapters, one check

An organisation keeps one design system. Nextcloud and OpenProject read it through their own adapter and come out the same. The OpenProject adapter is a proposal, not a product.

1

An admin picks or edits a design system once

In thematiq, for the whole installation. Both products follow.
2

One token set

Cunningham tokens, the system behind La Suite. Colours, type, radius, spacing, logos.
  • Primary bar, links
  • Action main button
  • Ink text
  • Lines borders, ground
  • Type family, scale
  • Radius corners
3

thematiq

Nextcloud app, exists today Exists
  • Reads the token set and writes Nextcloud theming variables for every app
  • Sets the logo, the primary colour and the type per installation
  • Already restyles the whole Conduction fleet
3

OpenProject plugin

Ruby gem, proposed Proposal
  • Maps the same tokens onto OpenProject's Primer CSS variables
  • Adds overrides for shell geometry: top bar, navigation, table, buttons, inputs
  • Reads the token set from the same place thematiq does, so one change lands in both
4

Nextcloud

Files, Mail, Calendar, Tasks and the apps
4

OpenProject

Work packages, Gantt, boards, meetings
5

Pixel-diff check

Shell and primitives of both products are rendered and compared on every release. A difference blocks the release until it is fixed.

Identical to the pixel

Top bar, navigation, type, colours, buttons, inputs, selects, dialogs, tables, tabs, badges and status dots. A user moving from one product to the other sees no difference in the shell.

Built from the same primitives

Gantt, the work package table, boards, team planner and backlogs have no Nextcloud counterpart. They use the shared buttons, inputs, tables and colours, and are not matched pixel for pixel.
